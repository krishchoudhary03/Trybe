SPEAKER 1: YOU ("ME") - SYSTEM LEAD & AI ARCHITECT
================================================================================
Role: Presentation Opener, Platform Vision & Conversational AI Engineering
Time: 4 - 5 Minutes

[A] LOGICAL NARRATIVE & PROBLEM STATEMENT (1.5 Mins)
  - The Problem: Most student career platforms either give static, one-size-fits-all 
    advice or rely on generic chatbots that hallucinate fake job opportunities, 
    miscalculate scores, or repeat robotic stock answers.
  - The Architectural Solution (Hybrid System):
    * TRYBE strictly separates "Reasoning & Hard Math" from "Coaching & Explanations".
    * Hard scores and roadmaps are deterministically computed by rules.
    * The LLM acts purely as an intelligent, conversational mentor that guides 
      the student without ever hallucinating data.

[B] TECHNICAL DEEP-DIVE (2 Mins)
  - Groq API Integration (openai/gpt-oss-120b):
    * High-speed inference using a 120-Billion parameter open-source model.
    * Sub-2-second latency for real-time conversation via server/aiProxy.ts.
  - Multi-Turn Context Serialization:
    * Instead of treating each user prompt in isolation, previous conversation 
      turns are serialized into structured { role: 'user' | 'assistant', content } 
      arrays, preserving dialogue continuity.
    * Context Injection: Student snapshot (target role, skill scores, open tasks) 
      is fed into the model prompt.
  - Guardrails & Strict JSON Schema:
    * Uses Groq's response_format: { type: 'json_object' }.
    * Output is validated by src/ai/validators.ts. Rejects any response referencing 
      skills or opportunity IDs not present in verified TRYBE data.
  - Multi-Tier Failover Chain:
    * Primary: Groq API (openai/gpt-oss-120b)
    * Fallback 1: Google Gemini (gemini-2.5-flash)
    * Fallback 2: Enhanced Local Rules Engine (src/career/engine/copilotLocal.ts)

SPEAKER 2: KAVYA - CORE ALGORITHMS & CAREER ENGINE SPECIALIST
================================================================================
Role: Mathematical Brain, Readiness Scoring & Adaptive Scheduling
Time: 4 - 5 Minutes

[A] LOGICAL NARRATIVE & ALGORITHMIC INTEGRITY (1.5 Mins)
  - The Problem: Career readiness cannot be arbitrary. If a student checks their score 
    today and it is 75%, and tomorrow an LLM outputs 60%, trust is broken.
  - The Algorithmic Solution (Deterministic Fairness):
    * Every percentage and timeline is backed by closed-form mathematical equations.
    * 100% reproducible, verifiable, and transparent to the student and recruiters.

[B] TECHNICAL DEEP-DIVE (2 Mins)
  - Multi-Factor Career Readiness Formula:
    * Readiness = sum(Weight_i * Score_i)
    * Breakdown:
      - 40% Target Role Skill Coverage (Matching student skills to industry role target)
      - 25% Verified Assessment Score (Interactive test results)
      - 20% Project Evidence (Real portfolio projects demonstrating practical use)
      - 15% Certifications & Mentor Action Items
  - Skill Gap Impact Analysis:
    * For every target skill s:
      Gap(s) = max(0, TargetLevel(s) - CurrentLevel(s))
    * Impact Weighting: Prioritizes gaps by how critical the skill is to the target role 
      (e.g., Node.js has higher impact for a Full-Stack Developer than CSS).
  - Dynamic Roadmap Engine (src/career/engine/roadmap.ts):
    * Graph-based milestone breakdown: Foundation -> Core -> Advanced -> Capstone.
    * Adapts dynamically: If the student changes weekly learning hours from 10h to 5h, 
      estimated completion dates adapt instantly without breaking task dependencies.
  - Opportunity Matching Engine (src/career/engine/opportunities.ts):
    * Scores active internships/jobs against student profile based on required skills, 
      preferred skills, and days remaining before deadlines.

SPEAKER 3: KRISH - INFRASTRUCTURE, DATABASE & SECURITY ARCHITECT
================================================================================
Role: Database Design, Row-Level Security & High-Performance Synchronization
Time: 4 - 5 Minutes

[A] LOGICAL NARRATIVE & DATA ARCHITECTURE (1.5 Mins)
  - The Problem: Career platforms store sensitive personal data (resumes, test scores, 
    private mentor notes) right alongside public campus data (events, clubs, feed).
    Client-side security is not enough; the database itself must enforce privacy.
  - The Infrastructure Solution (Database-Level Zero-Trust):
    * Pushing authorization directly into PostgreSQL via Supabase Row-Level Security (RLS).
    * Blending remote cloud synchronization with optimistic local-first caching for a 
      0-millisecond latency user experience.

[B] TECHNICAL DEEP-DIVE (2 Mins)
  - Relational Schema Design (38 Normalized Tables):
    * Clean entity-relationship model covering Auth, Colleges, Clubs, Skills, Roles, 
      Roadmaps, Assessments, Opportunities, and Private Chat.
    * Foreign key constraints, cascade rules, and indexing for rapid query execution.
  - Row-Level Security (RLS) Policies:
    * Public Catalog: Colleges, Skills, Career Roles are accessible to all authenticated 
      users: FOR SELECT TO authenticated USING (true).
    * Private Data: Assessments, Resumes, Roadmaps, and Chat Threads strictly enforce 
      ownership: auth.uid() = user_id.
    * An anonymous or unauthorized query to private tables returns 0 rows at the DB engine level.
  - PostgreSQL Stored Procedures (RPC Functions):
    * Custom RPC functions such as toggle_post_reaction(post_id, user_id) handle atomic 
      database mutations, preventing race conditions.
  - Local-First State & Optimistic UI:
    * Implemented in src/context/AppContext.tsx and src/context/CareerContext.tsx.
    * Immediate render from local state (0ms cold start), followed by asynchronous 
      background hydration with live Supabase data.

TEAM Q&A DEFENSE CHEAT SHEET (WHO ANSWERS WHAT)
================================================================================

Q1: "How do you guarantee your AI doesn't hallucinate fake career advice or jobs?"
-> ANSWERED BY: You ("Me")
-> KEY POINTS:
   * Prompt engineering uses strict HARD RULES.
   * Student snapshot (skills, assessment scores, verified opportunities) is injected.
   * validators.ts validates the output JSON against a whitelist of valid IDs before 
     rendering to the UI. If a non-existent job ID is generated, it gets rejected.

Q2: "Why didn't you just let the AI calculate the student's readiness score?"
-> ANSWERED BY: Kavya
-> KEY POINTS:
   * LLMs are probabilistic, non-deterministic language models, not calculators.
   * If a student's score fluctuates due to model temperature, trust is lost.
   * The career engine uses closed-form mathematical equations so the student has a 
     clear, verifiable checklist of what to improve.

Q3: "How is student data protected from other users on the platform?"
-> ANSWERED BY: Krish
-> KEY POINTS:
   * We do not rely on frontend checks alone.
   * PostgreSQL Row-Level Security (RLS) policies enforce auth.uid() = user_id on all 
     private tables (resumes, assessments, chat threads).
   * Even direct API calls with stolen IDs cannot access another student's data.

Q4: "What happens if the student loses internet connection or the Groq API is down?"
-> ANSWERED BY: You & Krish
-> KEY POINTS:
   * Krish: Local-first caching in AppContext ensures the app loads and functions offline.
   * You: The AI architecture has a multi-tier fallback: Groq -> Gemini -> Local Rules 
     Engine (copilotLocal.ts), so the student always gets an answer.
